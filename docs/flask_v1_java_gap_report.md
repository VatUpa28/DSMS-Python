# Flask V1 workflow gap report

| Feature | Java behavior | Current Flask behavior | Flask assessment | Exact Flask files involved | Exact Java files used as reference | Recommended Flask action |
|---|---|---|---|---|---|---|
| HOLD exclusivity | Only `AVAILABLE` Stones may be held; a client is required; the operation locks and validates the entire distinct batch before changing any Stone. | `POST /hold-stones` updates every submitted ID to `H` with no client existence, status, ownership, or batch validation. | unsafe | `backend/routes/inventory.py`, `frontend/templates/inventory.html`, `frontend/static/js/stones.js` | `services/HoldService.java`, `controller/HoldController.java`, `dto/StoneStatus.java`, `test/controller/HoldIntegrationTest.java` | Add transactional server-side hold/release workflows, validate client and every Stone, and reject mixed or foreign-held batches. |
| Client-aware inventory eligibility | Memo and direct-invoice validation permits only `AVAILABLE` or `HOLD` for the selected client; foreign holds are conflicts. | Transaction selection queries only `s.status = 'Y'`; creation does not validate status or `hold_client_id` on the server. | unsafe | `backend/routes/transactions.py`, `frontend/templates/transactions/transactions.html` | `services/TransactionService.java`, `repository/StoneRepository.java`, `dto/StoneStatus.java` | Revalidate distinct selected Stones inside a write transaction using legacy `Y`/`H` values and the selected client. |
| `RETURN_PENDING` | Memo and invoice returns set the Stone to `RETURN_PENDING`; it cannot be reused until receiving. | Returns set `B`; the meaning is implicit and no explicit `RETURN_PENDING` value exists. | partial | `backend/routes/transactions.py`, `backend/routes/returns.py`, `frontend/static/js/returns.js` | `dto/StoneStatus.java`, `services/TransactionService.java`, `resources/db/migration/V4__support_return_pending_and_receiving.sql` | Store `RETURN_PENDING` explicitly and reject it in hold/memo/invoice eligibility. |
| Physical receiving | A distinct receiving workflow accepts only `RETURN_PENDING`, writes a receiving event with authenticated receiver and timestamp, then changes to `AVAILABLE` atomically. | Both receive endpoints update submitted IDs to `Y`; one does not check state and neither records a receiver, event, or duplicate-receipt failure. | unsafe | `backend/routes/transactions.py`, `backend/routes/returns.py`, `frontend/static/js/returns.js` | `services/ReceivingService.java`, `controller/ReceivingController.java`, `entity/ReceivingEvent.java`, `resources/db/migration/V4__support_return_pending_and_receiving.sql`, `test/controller/ReceivingIntegrationTest.java` | Add `receiving_events` and a transactional receiving service; accept only `RETURN_PENDING`. |
| Generated transaction numbers | Counter rows provide independent type/date sequences and produce `MEMO-YYYYMMDD-####`, `INV-YYYYMMDD-####`, and `CR-YYYYMMDD-####` inside the transaction. | `generate_transaction_number` uses the current date and the lexically last existing number, with legacy prefixes and three digits; it is not safe under concurrent creation. | unsafe | `backend/utils/generate_transaction_number.py`, `backend/routes/transactions.py` | `services/TransactionNumberService.java`, `entity/TransactionNumberCounter.java`, `resources/db/migration/V6__create_transaction_number_counters.sql`, `test/services/TransactionNumberServiceIntegrationTest.java` | Add a SQLite counter table and allocate numbers inside the same write transaction; leave legacy numbers unchanged. |
| Shipping snapshots | A transaction stores source address ID plus copied Ship To fields; source ownership is validated and later address edits do not alter the transaction. | `transactions` retains only a live `ship_to_address_id`; the memo form posts one unpersisted address string and creation ignores it. | missing | `backend/database/schema.sql`, `backend/routes/transactions.py`, `frontend/templates/transactions/transactions.html`, `frontend/static/js/transactions.js` | `entity/Transaction.java`, `dto/TransactionRequest.java`, `dto/TransactionMapper.java`, `services/TransactionService.java`, `resources/db/migration/V8__add_transaction_shipping_snapshots.sql` | Add snapshot columns, validate source ownership, persist manual/copy values on new transactions, and read snapshots for new records. |
| Direct manual invoices | Authenticated accounting/admin/manager users can create an active invoice without a parent memo; all Stone/item snapshots and status changes are atomic. | No direct-invoice endpoint exists. Both existing invoice routes require a memo; one references an unset `invoice_id`. | missing | `backend/routes/transactions.py`, `frontend/templates/transactions/transactions.html` | `controller/TransactionController.java`, `services/TransactionService.java`, `dto/TransactionRequest.java`, `test/controller/TransactionControllerIntegrationTest.java` | Add a JSON/form-capable direct invoice backend route with a `NULL` parent, generated number, snapshots, and all-or-nothing eligibility checks. |
| Atomic memo activation | Activation locks the draft and its Stones, revalidates eligibility, moves items to active and Stones to memo, and clears a same-client hold in one transaction. | Confirmation updates transaction, items, and Stones independently without status/owner revalidation or rollback handling. | unsafe | `backend/routes/transactions.py`, `frontend/templates/transactions/transactions.html` | `services/TransactionService.java`, `test/controller/MemoActivationIntegrationTest.java` | Route confirmation through one SQLite write transaction and revalidate every item before changing it. |
| Partial returns | Selected active memo items become `RETURNED`; selected invoice items become `RETURNED` while copied credit items become `CREDITED`; transaction status is recalculated. | Memo route accepts arbitrary submitted IDs, uses `return`, and sets Stones to `B`. Credit route is partial but also uses `B` and lacks transactional validation. | unsafe | `backend/routes/transactions.py`, `frontend/templates/transactions/transaction_detail.html` | `services/TransactionService.java`, `dto/TransactionItemStatus.java`, `test/controller/TransactionWorkflowIntegrationTest.java` | Validate selected distinct source items and their current Stone statuses; use `RETURN_PENDING` and legacy-compatible `returned`/`credited` item values atomically. |
| Partial memo-to-invoice | Selected active memo items become invoiced, copied invoice snapshots point to the source item, Stones become sold, and memo status is recalculated. | A second memo-to-invoice route supports selected items but lacks locking/revalidation/snapshot shipping and never marks source items invoiced. A separate route is defective. | unsafe | `backend/routes/transactions.py`, `frontend/templates/transactions/transaction_detail.html` | `services/TransactionService.java`, `dto/TransactionMapper.java`, `test/controller/TransactionWorkflowIntegrationTest.java` | Consolidate the route behind a transactional workflow; preserve the existing page contract. |
| Authentication and role authorization | Password hashes, current authenticated identity, roles, backend endpoint authorization, and bearer-token security are implemented. | No login, users table, password hashing, current-user identity, role storage, backend role checks, or CSRF protection is present. | missing | `backend/app.py`, `backend/config.py`, all `backend/routes/*.py` mutation routes | `config/SecurityConfig.java`, `services/AuthService.java`, `controller/AuthController.java`, `entity/User.java`, `entity/UserRole.java`, `test/controller/AuthenticationIntegrationTest.java` | Add a minimal Flask session-auth foundation with hashed passwords and role decorators for the new workflow routes; do not add a user-management UI in this scope. CSRF remains a follow-up because the legacy form pages have no token infrastructure. |
| Audit logging | Java has an `audit_logs` store and records Stone/grading changes; HOLD and receiving retain dedicated history records. | No audit table or workflow history exists. | missing | `backend/database/schema.sql`, `backend/routes/inventory.py`, `backend/routes/transactions.py` | `entity/AuditLog.java`, `services/AuditService.java`, `entity/StoneHoldEvent.java`, `entity/ReceivingEvent.java`, `resources/db/migration/V2__create_users_and_audit_log.sql` | Add receiving history in this foundation (required for physical receipt); defer broad audit and hold-history UI/logging to a later scoped task. |
